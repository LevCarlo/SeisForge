# 07 ZZ cross-correlation, stacking and SAC export

Compute daily vertical-component (ZZ) ambient-noise cross-correlation sums from
a pre-prepared standard SDS MiniSEED archive, stream the daily NetCDF4/HDF5
files into a multi-day stack, and selectively export station pairs to SAC for
AFTAN or external tools.

The synthetic 1 Hz, 3-station, 2-day SDS archive is generated by
`tools/make_example_07_ccf.py` with known interstation delays:
`STA01 -> STA02` at **+8 s**, `STA01 -> STA03` at **+14 s**, and
`STA02 -> STA03` at **+6 s**. Method details and input contract:
[ZZ cross-correlation and stacking](../../docs/ant/ccf.md).

## Input

| file | what it is |
|---|---|
| `data/SDS/2026/XX/STA0{1,2,3}/LHZ.D/*.D.2026.00{1,2}` | 2 UTC days of 1 Hz FLOAT32 MiniSEED in standard SDS layout |
| `stations.csv` | station coordinates, SEED IDs, and uniform `response_state` |
| `ccf.yml` | daily ZZ cross-correlation settings |
| `ccf_stack.yml` | multi-day stacking settings |

## Run

```bash
bash run.sh
```

Takes ~1–2 s. Re-running `seisforge ant ccf -c ccf.yml` resumes existing days
when parameters, station table, and input files are unchanged. Delete `output/`
to run from scratch.

## Output

| file | what it is |
|---|---|
| `output/daily_ccf/ccf_ZZ_2026-01-0{1,2}.nc` | daily unnormalized ZZ sums (`ccf_sum`) and integer `n_windows` |
| `output/daily_ccf/ccf.log` | per-day status, active pairs, elapsed time, provenance |
| `output/stacked_ZZ.nc` | multi-day linear stack (`ccf`, `n_windows`, `n_days`, geometry) |
| `output/stack_ccf.log` | stacking summary and provenance |
| `output/sac_ZZ/XX.STA*_XX.STA*_ZZ.sac` | selectively exported SAC files with WGS84 geometry headers |

## How to tell the result is right

In `output/stacked_ZZ.nc` (and the exported SAC files), the cross-correlation
peaks should sit at **+8.0 s** (`XX.STA01` → `XX.STA02`), **+14.0 s**
(`XX.STA01` → `XX.STA03`), and **+6.0 s** (`XX.STA02` → `XX.STA03`).

Common issues on real data:

- **`off the absolute k/fs grid`**: traces in SDS are not aligned to UTC
  `k / sampling_rate_hz` within `grid_tolerance_samples`. Align them during
  data preparation before running `ccf`.
- **`mixing response states`**: stations in `stations.csv` declare different
  `response_state` values. Keep one uniform state across the run.
- **`falls outside declared input valid_passband_hz`**: whitening corners
  extend past the declared valid passband of your prepared SDS data.

## Using your own data

Copy this folder (`examples/07_ccf/`) and edit the lines marked `# change this`
in `ccf.yml`:

1. Point `input.sds_root` to your pre-prepared SDS directory and replace
   `stations.csv` with your stations.
2. Set `input.sampling_rate_hz`, `input.response_state`, and
   `input.valid_passband_hz` to match your prepared SDS data (e.g. `20.0` Hz
   for nodal arrays, `max_lag_s: 60.0`, `lag_guard_s: 20.0`).
3. Update `run.start_date` / `run.end_date` (or submit one day per task on an
   HPC cluster with `seisforge ant ccf -c ccf.yml --date YYYY-MM-DD`).
